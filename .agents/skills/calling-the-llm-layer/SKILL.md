# Calling the LLM layer

## When to use
Editing `src/llm.js`, changing any OpenRouter/DeepSeek call, prompt, json schema, reasoning effort, or model; or debugging a 400/401 from either provider.

## Injected knowledge
- **Reasoning effort: Pro uses `xhigh`, Flash uses `high` (mechanical stages can use `medium` — accepted by DeepSeek V4, probed HTTP 200). Never `max`** (HTTP 400; guard rebaixa p/ xhigh). Send only the nested `reasoning` object. No provedor DIRETO (LLM_PROVIDER=deepseek) o `reasoning` NÃO é enviado (param do OpenRouter) — o effort efetivo é o default `high` da API (mapeamento oficial medium→high, xhigh→high; `max` existe no direto, mas nunca enviamos). `src/llm.js:28-29@79fd5d8`, `src/llm.js:139-146@d17d599`, `config/models.json:14-18@d17d599`.
- **PROVIDER: OpenRouter (default) | DeepSeek DIRETO (api.deepseek.com).** `LLM_PROVIDER=openrouter|deepseek` no env — sem auto-detecção (inválido/ausente → openrouter; `clampProvider`, `src/config.js`). O provider ativo decide transporte, chave e fonte do custo. **Transporte por provider (`src/llm.js` `client()`/`createOnce`):** no direto a base vira `DEEPSEEK_BASE_URL` (default `https://api.deepseek.com`; o SDK openai anexa /chat/completions), o body OMITE os params da OpenRouter (`reasoning` e `usage:{include:true}` — a API os ignora/usa outra semântica) e o `response_format` degrada p/ `json_object` (`responseFormat` em llm.js; json_schema NÃO é suportado no direto — docs §4 — o zod/parse defensivo seguem como guarda; prompts já dizem "responda apenas com JSON"). **Custo LOCAL no direto:** a API NÃO traz `usage.cost` — `computeUsageCost(usage, model)` (`src/config.js`) multiplica prompt/completion_tokens × tabela (`DEEPSEEK_PRICES` const, overrides por env `DEEPSEEK_PRICES` JSON ou `DEEPSEEK_PRICE_<MODEL>_{INPUT,OUTPUT}_PER_M`, `DEEPSEEK_PRICE_DEFAULT` = base flash) e INJETA o cost no usage ANTES do commit do ledger (`budget.js` lê `usage.cost` e fica INTOCADO). O CLI cobra input CHEIO (sem distinção cache hit/miss — o webapp usa `prompt_cache_hit_tokens` com tarifa de hit; ver building-the-webapp). **Slugs:** `translateModel` (`src/config.js`) resolve no direto (`deepseek/deepseek-v4-flash-0731` → `deepseek-v4-flash`; tabela `DEEPSEEK_DIRECT_SLUGS` + overrides `DEEPSEEK_MODEL_MAP`/`DEEPSEEK_DEFAULT_MODEL`; slug sem `/` já é direto; fora da tabela SEM `DEEPSEEK_DEFAULT_MODEL` fica INALTERADO, fail-open) e é IDENTIDADE no openrouter — `STAGE_MODELS`/`config/models.json` continuam em slug OpenRouter. **Chave em runtime:** `setRuntimeKey(key, provider = provider atual)` (`src/config.js`) troca provider+chave de uma vez; `DEEPSEEK_API_KEY`/`OPENROUTER_API_KEY`/`LLM_PROVIDER`/`HAS_LLM` são `export let` (live bindings); `client()` recria o SDK quando provider OU key mudam (`_clientProvider`/`_clientKey`). **Preços:** fonte ÚNICA = `docs/deepseek-direct.md` (§6). Atualização: CLI = env `DEEPSEEK_PRICES`/`DEEPSEEK_PRICE_*` (sem deploy); webapp = const `DEEPSEEK_PRICES` em `webapp/src/lib/openrouter.js` + redeploy via `npm run deploy` — RISCO DE DRIFT entre as duas tabelas (e a de cache-hit, que só o webapp tem). NOTA: a DeepSeek migra p/ preço **peak/off-peak em 2026-08-16 16:00 UTC** (off-peak = metade do peak; sobretaxa 2× nas janelas UTC 01:00–04:00/06:00–10:00) — **re-verificar as duas tabelas + `docs/deepseek-direct.md` após essa data** (handoff não-bloqueante).
- **Two-tier strategy.** Pro (xhigh) derives reusable selectors and classifies: `deriveLinkSelector`, `deriveContentSelector`, `classifyFacet`, `mapQueryToFacetTags`. Flash does the cheap high-volume work: `deriveNextLink`, `extractLinksItemByItem`, `extractArticleViaLLM`, `extractRoundupLinks`, `summarizeArticle`, `judgeRelevance`, **`judgeRelevanceBatch` (busca soft da web, xhigh)**, `curateRoundupItems`/`curateLeftoverLinks` (curadoria, high), `cleanArticleContent` (limpeza, medium), `verifyRecordLLM` (verificação, high), `deriveDateSelector` (spec de data CSS+regex, high) — stages resolved via `stageModel()` (config/models.json + env). `src/llm.js:359-600@d17d599`, `src/config.js:145-201@d17d599`.
- **Classify cost (multi-faceta = ALTO volume, cuidado).** `classifyOne` (`src/classify.js:17-47`) faz **1 chamada por faceta** (`getFacets()`, 9) por artigo — SEM lote. Modelo POR FACETA (`classifyFacetModel`, `src/config.js:292`): sem override herda a etapa base `classify`; `classify:<faceta>` (models.json) ou env `LLM_MODEL_CLASSIFY_<FACETA>`/`LLM_EFFORT_CLASSIFY_<FACETA>` trocam. Anti-padrão custoso (já foi ~92% do gasto de uma coleta longa): 6 facetas no **Pro/xhigh** com o **corpo inteiro reenviado 9×**. Perfil barato atual (config/models.json): só as CORE `domain`+`topic-technology` no Pro/high; as outras 7 em Flash/medium; input recortado por `CLASSIFY_MAX_CHARS`=2000. Pro≈10×Flash/chamada (seeds `src/budget.js:12`) — meça com `ncrawl finish --no-verify --no-summarize` (só o sweep de classify; byStage no extrato). Salto FUTURO (deferido): classificar em LOTE de artigos por chamada reusando `judgeRelevanceBatch`+`mergeBatchVerdicts`.
- **SMALL-OUTPUT RULE (hard-won).** A high-volume stage must return SMALL DATA (spans, items, verdicts), never long rewritten text: the first `articleClean` asked for the full cleaned body back and STARVED the pipeline — 18 in-flight calls, ZERO commits in 8+ minutes (reasoning + thousands of output tokens per call, then 180s timeout + retry chains) while a trivial probe answered in 2s. Redesigned to verbatim `junk_spans` (local deletion), calls land in seconds. Cost per article: ~$0.001. `src/llm.js:466-530@d17d599`, `src/clean.js:38-60@d17d599`. Verified: live A/B nos runs 3 (travado) e 4+ (fluido).
- **`max_tokens` do body = teto de SAÍDA + folga de RACIOCÍNIO (medido 2026-10-11).** Em modelos de raciocínio o `max_tokens` cobre reasoning + CONTEÚDO: usar o teto de saída (`stageMaxTokens`) como total faz o raciocínio comer tudo (`reasoning_tokens == completion_tokens == max_tokens`) e a resposta vem com `content` VAZIO — 101 chamadas truncadas (`finish_reason=length`) numa run (contentSelector 33/56, classify 22/561, articleClean 11/73) que o parse lia como "JSON inválido" e as retentativas REPAGAVAM o raciocínio. Hoje: `body.max_tokens = stageMaxTokens(stage) + reasoningTokensAllowance()` (folga `LLM_REASONING_ALLOWANCE`, default 8.000; 0 = antigo) e o guard degenerado separa CONTEÚDO (`completion − reasoning > 1.2×` do teto de saída = loop de geração) de total (`> 1.2×` do enviado = provider ignorou o max_tokens). A folga é TETO, não alvo (verifyRecord p50=193 num teto de 3.000; o modelo não infla). `src/config.js` (`STAGE_MAX_TOKENS`/`reasoningTokensAllowance`), `src/llm.js` (`createOnce`/`callJSON`), `test/llm.guards.test.js`. Verified: run pós-fix = 139 parses ok, 0 `json-retry`, 0 truncamentos (vs 36 retries + 8 falhas + 101 truncamentos na pré-fix).
- **Retry de TRANSPORTE para além do 429 (medido 2026-10-11).** Só 429 e JSON inválido re-tentavam: um hang do provider cortado pelo `AbortSignal.timeout` (180s) matava a chamada e a faceta ficava perdida (artigo `partial` — 16/137 classify num burst). Hoje `isTransientTransportError(e, jobSignal)` re-tenta (máx. 2) hangs/rede/5xx; 4xx (pedido/key) e abort do JOB (deadline/cancel — `jobSignal.aborted`) nunca re-tentam. Chamadas que penduram SEMPRE (raciocínio lento até ao limite em prompts específicos — tipicamente facetas de vocabulário grande) NÃO são transitórias: 3×180s e a faceta não-obrigatória continua `partial` (fail-open por design, `failedMandatoryFacets` só protege as obrigatórias); recuperar parciais re-classificando com `classifyArticleRow` (upsert limpo de classificação + tags). `src/llm.js`, `src/classify.js`, `test/llm.guards.test.js`.
- **Batch judging (stage `searchBatch`): rubrica compartilhada + eco de id + fusão tolerante.** `judgeRelevanceBatch({query, items})` julga ~40 artigos por chamada (itens = 1 JSON por linha `{id,title,summary}`; saída pequena `{results:[{id,relation,kind}]}` — respeita a small-output rule). A rubrica/few-shots são a MESMA const `RELEVANCE_RUBRIC` do `judgeRelevance` unitário (texto escolhido por eval — F1 0.848 vs 0.731; NÃO reescrever sem re-rodar o eval), então soft e deep julgam com o mesmo critério. O prompt exige eco EXATO do id, mas a garantia real fica no CHAMADOR: `mergeBatchVerdicts` (search.js) trata id faltando→`none` fail-open, id inventado→ignorado, duplicado→1º vence; zod usa `z.coerce.number().int()` no id (o modelo às vezes ecoa string) e clamps de relation/kind. `src/llm.js@6b1d77d`, `src/search.js@6b1d77d`. Verified: `test/search.batch.test.js` + busca soft real (362 artigos/10 lotes, 0 ids perdidos).
- **Structured output + defensive parse + retry/escalation.** `response_format` json_schema `strict:true` + zod em TUDO (no provedor DIRETO degrada p/ `json_object` — ver bullet PROVIDER; o zod/clamp continuam como backstop); enums NÃO vão no json_schema (suporte não comprovado) — o clamp fica no zod (`kind` desconhecido -> 'news', `verdict` -> 'suspect'), com backstops determinísticos fora do LLM (SPONSOR_RE, isRealRecoveredItem, applyJunkSpans+sanityCheckCleaned). `callJSON` re-samples até `retries` no MESMO modelo e escala p/ Pro na última tentativa (Flash trunca JSON às vezes). `src/llm.js:114-172@d17d599`.
- **Roundup curation is PER-SECTION now.** `splitIntoSections` (curate.js) fatia a edição por seção (heading markdown / negrito / rótulo com emoji reconhecidos por `sectionTitleOf`) e dispara 1 `curateRoundupItems` por seção EM PARALELO, cada um com um `sectionHint` (Releases -> tende a release, Code&Tools -> tool, etc. — só um viés, o agente decide item a item). Mais paralelismo intra-edição (uma issue vira ~3–5 agentes) e prompts especializados; sem seções detectáveis, cai p/ chunk por tamanho. Guards do sectionTitleOf (verificados por repro): linha com URL/`](` NUNCA é rótulo (heading de ITEM como `## [Deno 2.9](url)` fatiava o item p/ fora do contexto) e rótulo solto não termina em `[.!?…]` (frase de prosa com palavra de seção virava seção). `src/curate.js@40d0505`, `src/llm.js@40d0505` (`sectionHint`/`curateRoundupItems({section})`). Verified: run #12 — 629→3, 630→5, 631→3 seções; 67 itens (vs 59 no modo chunk).
- **Curator recall is NOT guaranteed** — even with a good prompt the first pass omitted mid-page headline items; nunca confie numa única passada p/ completude. O par determinístico (diferença de conjuntos de links sobre o HTML BRUTO) + passe de cobertura dedicado (com a página INTEIRA podada como contexto) é quem garante. `src/curate.js@40d0505`. Verified: coverage event mostra leftovers/recovered por URL; os 3 itens que o Readability escondia entraram.
- **Transport.** SDK openai -> baseURL POR PROVIDER (OpenRouter `https://openrouter.ai/api/v1` com `HTTP-Referer`/`X-Title`; direto `DEEPSEEK_BASE_URL`, sem esses headers — não existem lá); `maxRetries:1` + `LLM_TIMEOUT_MS` 180s; penalidade de 429 COMPARTILHADA (backoff exponencial, teto 60s) + `reportRateLimit` halva a lane llm E o **teto calibrado** (`st.llmCap`, governador): o grow +1/10s não passa dele — converge no nível sem 429 em vez de oscilar; fim de run persiste `GOVERNOR_LLM_CAP` em NC_HOME/.env (`persistLlmCalibration`; `limits set --llm-cap N` ajusta/limpa); no OpenRouter `usage: {include: true}` traz o custo REAL p/ o ledger (commit ANTES do parse — 200 malformado também custou); no direto o `usage` sempre vem e o cost é INJETADO localmente (ver bullet PROVIDER). `callJSON`/`createOnce` aceitam `signal` (AbortSignal do job, repassado como request option do SDK: `create(body, {signal})`): o teto duro do job cancela a chamada EM VOO e devolve o slot da lane; o retry de 429 e cada tentativa checam `signal.aborted` antes de admitir de novo. Entry points do job de artigo já plugados: `cleanArticleContent`/`deriveContentSelector`/`extractArticleViaLLM` (`{signal}` opcional — chamadas avulsas seguem sem). `src/llm.js:14-103@d17d599`, `src/llm.js@3351a58`. Verified: run #3 real (0 zumbis segurando a lane llm) + npm test verde.
- **Token discipline.** `pruneForLLM` + clamp (`MAX_HTML_FOR_LLM`, `CLEAN_MAX_CHARS`, `VERIFY_MAX_CHARS`, `SEARCH_MAX_CHARS`) antes de enviar. Curadoria usa MARKDOWN do corpo Readability (5KB limpos numa issue de 140KB de HTML). Lote da busca soft: título ≤200 + summary ≤400 chars por item. `src/curate.js:108-115@d17d599`.
- **The `.env` key override gotcha + runtime key.** `config.js` loads repo `.env` then `NC_HOME/.env` OVERRIDING shell vars — a stale exported key otherwise yields `401 "User not found"`. Probe OpenRouter: `curl -s https://openrouter.ai/api/v1/key -H "Authorization: Bearer <key>"`. `OPENROUTER_API_KEY`/`DEEPSEEK_API_KEY`/`HAS_LLM`/`LLM_PROVIDER` são **`export let` (live bindings ESM)** + `setRuntimeKey(key, provider = provider atual)`: a web UI (POST /api/key) e o `cmdKey set` ativam a key SEM reiniciar e sem tocar nenhum call site; o `client()` cacheia por (key, provider) (`_clientKey`/`_clientProvider`) e reconstrói quando qualquer um muda. NÃO capture a key numa const local ao importar. `src/config.js@6b1d77d`, `src/llm.js@6b1d77d`. Verified: `test/config.key.test.js` + key/status dinâmico em `test/web.search.test.js`.

- **Etapa `searchSpec` + prompt de lote SPEC-AWARE (busca precisão-primeiro).** `compileQuerySpec(query)` (stage `searchSpec`, Pro/high) devolve `{must_have, nice_to_have, query_en, terms}` (small-output: só listas curtas; critérios + tradução PT→EN). GOTCHA: um stage NOVO PRECISA entrar em `STAGE_KEYS` (`src/config.js`) — senão `stageModel` cai no default `{Pro, xhigh}` e o `models.json` da etapa é IGNORADO (foi o que fez o spec rodar a xhigh/25s por engano; caso ATUAL: `articleReclean` (`verify.js:128`, reclean) tem chave Pro/high no models.json mas RODA Pro/xhigh via default — verificado por runtime 2026-08-13: `STAGE_KEYS.includes('articleReclean') === false`). `buildBatchJudgePrompt({query, items, spec})` é a FONTE ÚNICA do prompt de lote (exportada; `eval/prompts.mjs` a IMPORTA → eval == produção, respeita o eval-lock); `spec` presente injeta `specBlock` e redefine "direct" = satisfaz TODOS os OBRIGATÓRIOS (default-reject). `judgeRelevanceBatch`/`judgeRelevance` aceitam `spec` OPCIONAL (ausente = baseline v2_fewshot intacto). Effort de `searchBatch` = **medium** (eval de LOTE: mais preciso E ~37% mais rápido que xhigh; low piora o recall) — reasoning alto não compra precisão nesta tarefa de vocabulário fixo. `src/llm.js@f98220e`, `src/config.js@f98220e`, `config/models.json@f98220e`.
