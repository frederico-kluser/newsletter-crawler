# Persisting and orchestrating

## When to use
Editing `src/db.js` (schema/statements), `src/crawl.js`/`src/curate.js` (frontier/curation/pagination), `src/events.js` (event buffer), or `src/index.js` (loop); touching dedup or the queue.

## Injected knowledge
- **Schema.** Tables `sources`, `pages`, `articles`, `selectors`, `frontier`, `runs`, `llm_usage`, `classifications`, `article_tags`, `classification_uncovered`, **`events`** (run_id, source_id, url, stage, status, detail JSON — per-item pipeline trace read by `ncrawl inspect`), **`searches`** (histórico de buscas IA: run_id, origin cli|tui|web, query, mode, scope_json, stats_json, hits_json — hits guardam só ids+vereditos; custo real via JOIN run_id→llm_usage, re-hidratação por `searchArticlesByIds`/`webArticlesByIds`; `wipeAll` a inclui); `UNIQUE(url)`; UNIQUE `content_hash`; WAL + foreign_keys + busy_timeout. `src/db.js@d17d599`.
- **Event writes are BATCHED (fail-open).** `logEvent` pushes to an in-memory buffer; the flush inserts the whole buffer in ONE better-sqlite3 transaction — on `EVENTS_FLUSH_AT` (50) or the explicit `flushEvents()` in `runWithLimits`'s `finally`. Cuts the fsync of thousands of tiny inserts. Trade-off: a HARD kill loses the un-flushed tail (telemetry only). A separate crawl process reading events (inspect) sees only committed rows. `src/events.js@40d0505`, `src/commands.js@40d0505`. Verified: `test/events.buffer.test.js` (auto-flush at threshold + explicit flush).
- **Articles quality columns (ensureColumn):** `kind` (news|tool|release), `issue_url`/`section`/`blurb`, `content_source` ('aggregator'|'target'), `needs_enrich`, `cleaned`, `verify_status`/`verify_notes`. Selectors gain `date_selector/date_attribute/date_regex`. All migrations idempotent via `ensureColumn`; `wipeAll` includes `events`. `src/db.js:137-186@d17d599`.
- **All SQL via one `stmts` object.** `claimNext` atomic UPDATE...RETURNING orders `retries ASC, id ASC`; `enqueue` INSERT OR IGNORE; ONE `insertArticle` serves both flows (needs_enrich distinguishes); `enrichArticle` fills target body WITHOUT touching kind/blurb/section; `requeueUrl` re-activates a done/failed job for a still-needs_enrich row; `requeueNeedsEnrichForSource` (run in the seed loop) re-activates ALL still-blurb-only article jobs of a source at crawl start (this is what makes the deadline's "enrich later" real). `src/db.js:68-132@79fd5d8`, `src/db.js:262-296,419-423@d17d599`, `src/db.js@40d0505`.
- **Busca: stmts de escopo + âncora do delta.** Os 4 stmts de busca (`listAllArticlesForSearch`, `listRunArticlesForSearch`, `articlesByTags(ForRun)`) trazem `source_name` (LEFT JOIN sources) + `date_iso` (`coalesce(iso_date(published_at), date(extracted_at))`) p/ a lista/preview da TUI. A busca IA da web tem WHERE próprio `SEARCH_SCOPE_WHERE` (`@sources` array JSON via json_each + from/to via iso_date) usado por `webSearchScopeCount`/`webSearchCandidates` (hard: content inteiro)/`webSearchCandidatesLite` (soft: summary_pt/blurb/substr(content,400)); hits re-selecionados por `webArticlesByIds` (mesmas colunas dos cards; ordem restaurada em JS via Map). **Âncora do escopo "apenas o novo" = `maxArticleRunId` (`MAX(articles.run_id)`), NUNCA `MAX(runs.id)`**: search/verify/web-search também abrem runs mas não setam `articles.run_id` — ancorar nelas zera o delta (bug real: MAX(runs.id)=3 vs artigos todos na run 1). `avgUsageByStage` (média real de custo por stage em llm_usage) alimenta as estimativas de US$ pré-busca. A função SQL `fold` foi REMOVIDA junto com a cláusula `@q` do `WEB_WHERE` (a busca por texto virou IA); `@kind` é CASE de 3 vias (release = coluna exata; release segue contando como tool). `src/db.js@6b1d77d`, `src/commands.js@6b1d77d` (`getSearchScope`). Verified: `test/web.search.test.js` + npm run status.
- **Register-at-curation, enrich-at-fetch, curated in ONE transaction (index sources).** `processRoundup` -> `curateRoundup`: the issue page becomes Readability markdown, split BY SECTION (`splitIntoSections`, 1 PARALLEL Flash agent per News/Tools/Releases/IN BRIEF) — see calling-the-llm-layer. Each curated item is INSERTED immediately (content = title+blurb, `needs_enrich=1`, published_at = issue date) and enqueued; the whole item loop runs inside a SINGLE `db.transaction` (batched writes; the loop is sync, logEvent only buffers). Enrichment keeps the blurb on thin/blocked/dup-content/timeout targets — a tool never disappears. Sponsors/jobs never saved (LLM label + deterministic SPONSOR_RE/JOB_RE). COVERAGE pass over RAW-page links (not the Readability body — it drops ad-adjacent blocks) + `isRealRecoveredItem` filter; the leftover agent gets the WHOLE pruned page as context. Curated items are exempt from the --since floor (issue is the anchor). `src/curate.js@40d0505`, `src/crawl.js:360-410@d17d599`. Verified: run #12 — 3 issues -> 3/5/3 sections, 67 items (kind+section), 0 sponsors, 0 docs-secondary; the 3 headline items Readability hid were all captured. **Custo da curadoria é FIXO por issue e roda ANTES do dedup**: ~7,3 chamadas (6,21 seções + cobertura; US$ 0,0132/issue) mesmo para issue cujos itens são todos dups — não existe guard "issue já coberta" no job roundup, a proteção é só o enfileiramento via `isUrlKnown` (ramos 3/4). Medido: run 2026-09-10 (pós-restore sem issue_url): 494 issues curadas, 176 só-dup (~US$ 2,32 de US$ 6,53), 9.107 itens dup vistos pela IA. `docs/reprocesso-IA-audit-2026-09-11.md` (Furo 5).
- **Frontier state machine + DEADLINE de TRABALHO com abort real.** `pending -> in_progress -> done | failed`; resume: `resetInProgress()` flips stale in_progress back to pending; `bumpRetry` até MAX_RETRIES; BUDGET_EXCEEDED devolve a pending sem consumir retry. O deadline do job de artigo NÃO é tempo de parede: `createJobClock(JOB_TIMEOUT_MS)` (`src/deadline.js@3351a58`) conta SÓ as fases de trabalho fetch/render/parse (`clock.run`); esperas de fila (lanes/politeness — `clock.wait`/`noteWait`) e as fases LLM ficam FORA do relógio (têm `LLM_TIMEOUT_MS`/orçamento próprios). Expirou => o clock ABORTA um AbortSignal e got/render/parse/LLM em voo PARAM, devolvendo as lanes — o `withTimeout` puro anterior não cancelava nada e o job estourado virava ZUMBI segurando as lanes, derrubando os seguintes em cascata (run real #1: 194/194 artigos estouraram, 0 salvos; com o clock, run #3: 0 estouros, 9 enriquecidos). `JOB_HARD_TIMEOUT_MS` (default 10x, 0=off) segue como teto DURO de parede via `withTimeout` por cima e, ao disparar, também aborta o clock (sem zumbi no backstop). O veredito de timeout no dispatch vem de `clock.expired()` (o abort pode aflorar como erro de cancelamento do got/SDK, não como code JOB_TIMEOUT). Timeout de enrich mantém frontier `done` + `needs_enrich=1` (re-enfileirado no próximo crawl); o evento `job/timeout` agora carrega `phases/waits` do clock — `ncrawl inspect` mostra ONDE o tempo foi. listing/roundup seguem ISENTOS do corte (cortar curadoria no meio joga fora o fan-out — bug real que já tivemos). `src/commands.js@3351a58`, `src/fetch.js@3351a58`. Verified: `test/deadline.clock.test.js` + `test/commands.timeout.test.js` + run #3 real (0 timeouts).
- **One `runs` row per command.** `runWithLimits`/`beginRun` opens the ledger run; crawlRun REUSES it as the delta watermark (`getBudgetState().runId`). A busca IA da web abre o run `web-search` por um mini-envelope PRÓPRIO no web.js (`withSearchRun`: initGovernor llm-only + beginRun/endRun; serializado — 1 busca por processo, 2ª leva 409) porque importar `runWithLimits` criaria ciclo commands.js↔web.js. `src/commands.js:127-140@d17d599`, `src/web.js@6b1d77d`.
- **Concurrency loop + STREAMING verify.** capacity = fetch+render lanes (governor); inflight Set + Promise.race. After a successful article save/enrich (processArticle returns `{verifyUrl}`), the loop schedules `verifyArticleRow` on the llm lane in a SEPARATE `verifying` set (does NOT count against fetch/render capacity); the loop waits on `[...inflight, ...verifying]`. So most fichas are verified DURING the crawl; the post-crawl `verifyPending` sweep stays as an idempotent (NULL-only) safety net for blurb-only leftovers. **Invariante das etapas NULL-idempotentes (verify/summarize/classify):** elas re-selecionam por coluna/linha AUSENTE (`verify_status IS NULL`, `summary_pt IS NULL`, `classifications` sem linha via `LEFT JOIN ... IS NULL`), então NUNCA podem PERSISTIR um resultado parcial/vazio numa falha de LLM — senão o item vira falso-positivo permanente, invisível ao sweep. verify/summarize são fail-safe por deixarem a exceção PROPAGAR até o catch do loop (a coluna fica NULL → re-selecionada). classify ERRAVA isso: um catch POR FACETA engolia o erro de rede/API e `persist` gravava `'partial'` zerado — corrigido: `classifyOne` lança `ClassifyIncompleteError` (mesmo contrato do `BUDGET_EXCEEDED`) quando uma faceta OBRIGATÓRIA erra (`ok:false`, distinto de `ok:true`+vazia legítima), o chamador não persiste e `listArticlesNeedingClassification` re-seleciona. `src/classify.js@1bae501`. Verified: `test/classify.incomplete.test.js` + prod (402 insufficient-credits → 49 artigos ficaram pendentes, 0 novos falsos-positivos; zero-tag 185→0). **Limitações medidas (run 2026-09-11, âncora --since 2026-09-05, docs/reprocesso-IA-audit-2026-09-11.md):** (a) kept-blurb DEVOLVE `verifyUrl` (crawl.js keepAggregatorVersion) e entra no STREAMING da própria run — antes ficava fora e o blurb virava dívida do sweep (~400 pendentes migrando entre runs); (b) os sweeps são NULL-only e o PÓS-CRAWL é ESCOPADO À RUN (`listArticles*ForRun` + `runId` em verifyPending/classifyPending/summarizePending): coleta de data já coberta não drena mais o backlog de runs anteriores (`--sweep-all` volta ao global; o `finish` sempre drena o pendente global) — antes do fix, 178/219 verifies da run de validação caíram em artigos antigos por isso; (c) o verify sweep usa heurísticas grátis quando possível (137/153 restaurados). O crawl também alimenta `src/progress.js@3351a58` (em memória, sem SQL): fases ativas (fetch/render/limpeza/curadoria/verificação/resumo/classificação), contadores (salvos/enriquecidos/blurb/estouros/itensCurados), fontes x/y (`sourceSeen` no seed, `sourceListingDone` no dispatch) e o % por DATA rumo ao `--since` (`dateSeen` nos itens datados/published; `floorHit` nas paradas por piso => 100%) — lido por `getRunTelemetry().progress` (painel TUI) e pela linha `progresso:` periódica do CLI (junto do costTimer). - **Date floor / dedup / purge / pagination / inspect** — `--since` pairs listing links with dates and stops pagination (curated items exempt); dedup = canonical URL + UNIQUE url + UNIQUE content_hash (curated content = `title — blurb`); `ncrawl purge <src> --yes [--selectors]`; pagination stops on empty/repeat-hash/no-next/`added===0`/below-floor/maxPages + **known-url** (parada determinística zero-LLM em `crawlArchive` e no fallback item-a-item: se TODOS os links da página já existem em articles/pages/frontier done — `stmts.isUrlKnown` — para ANTES de enfileirar; ≥50% loga 'território conhecido' e o `added===0` segue como rede de segurança. Motivo: frontier limpa transforma todo link em 'novo' e re-coletaria o arquivo inteiro); `ncrawl inspect` (latest CRAWL run via `getLatestCrawlRunId`) prints the per-issue tree + per-stage cost + skip reasons, `--url` the event timeline. `src/crawl.js@d17d599,a57b311`, `src/db.js:355@a57b311`, `src/commands.js:427-560@d17d599`.

- **Piso de data POR FONTE (cursor de captura).** `sources.cursor_date` guarda a data do item mais novo já capturado daquela fonte e a coleta seguinte repete esse piso em vez de varrer de novo — sem depender de um `--since` comum a todas. `src/cursor.js` (puro): `parseSinceSourceFlag` (`--since-source "Nome=AAAA-MM-DD[,Outro=...]"`) + `resolveSourceFloor({explicitSince, override, cursor, derived, minDate, maxDate})` com precedência override > `--since` > cursor > derivado > mínimo, clamp no mínimo e descarte de DATA FUTURA só para valor automático (cursor/derivado; flag explícita passa). `maxPublishedForSource` = `MAX(iso_date(published_at))` com teto em `date('now')` (nunca a string crua: "Sep 9, 2026" quebraria o MAX lexicográfico; data-bomba não deixa a fonte sem piso para sempre). O dispatch resolve o piso POR JOB (`floorBySource` por `source_id`); o cursor SÓ AVANÇA e SÓ depois de listagem bem-sucedida (`advanceSourceCursor`, CASE never-back); `purgeSource` zera na MESMA transação (senão a recaptura pós-purge seria pulada) e `--reset-cursor [fonte]` zera sob demanda (sozinho é quase no-op: o derivado devolve o mesmo MAX — recuperação real é `--since <data antiga>`). A página 1 da listagem é SEMPRE relida — o cursor limita a profundidade da paginação, nunca a descoberta. **TETO DE TRABALHO INACABADO (evita PERDA de backlog):** `oldestUnfinishedForSource` + `applyPendingCeiling` garantem que o piso NUNCA ultrapassa `pending/in_progress` da fonte — captura parcial (`--max-articles`/budget/Ctrl+C/deadline) deixaria roundups abaixo do piso, pulados por `below-since` e marcados `done`, e `enqueue` (INSERT OR IGNORE) + `isUrlKnown` (qualquer estado) nunca os trariam de volta; pendência sem data derruba para o piso mínimo. `enrichArticle` carimba `run_id` da run corrente (delta da busca e sweep escopado enxergam a ficha enriquecida). `src/cursor.js@2026-09-12`, `src/db.js`, `src/commands.js`. - **Camada de RESTORE no db.js (o acervo volta do git, nunca do zero).** `restoreSourceByName` (remapeia o id do snapshot p/ o id local), `restoreArticle` (INSERT OR IGNORE; `content_source='restore'`, `cleaned=1`, `needs_enrich=0`, `date_iso`→`published_at`, content_hash = o MESMO sha256(content) do crawl — conteúdo VAZIO grava hash NULL p/ não colidir no índice UNIQUE; `source_id` inexistente é PULADO com `reason:'bad-source'` porque `OR IGNORE` NÃO cobre violação de FK e derrubaria o restore NO MEIO), `restoreTags`, `markUrlDone` (frontier `done`; é a ÚNICA escrita sobre linha pré-existente — promove `failed`→`done`) e `restorePage` (issue → `pages`, status `restored`). - **`isUrlKnown` tem 4 ramos** — `articles.url` ∪ `pages.url` ∪ `frontier` em (done|failed|pending|in_progress) ∪ **`articles.issue_url`** — e é a parada determinística zero-LLM da paginação. O 4º ramo só rende se o snapshot carregar `issue_url`: o CÓDIGO já exporta (`webExportArticles` + src/export-web.js) e o restore alimenta `restorePage`, mas o `webapp/public/data/articles.json` COMMITADO hoje veio do exportador ANTIGO (0 ocorrências em 13.758 artigos). - **Teto de tentativas do enrich (fail-open por ALVO, não por run).** `articles.enrich_attempts` + `bumpFailedEnrichAttempts` no INÍCIO do crawl seguinte + `requeueNeedsEnrichForSource(source, ENRICH_MAX_ATTEMPTS=3)`: um alvo que falhou 3 rodadas seguidas para de ser re-enfileirado e fica com o blurb do agregador (`countEnrichAtCapForSource` reporta quantos). Sem o bump no início, o item era re-enfileirado PARA SEMPRE com `enrich_attempts` congelado em 0 — o teto nunca chegava, e um domínio morto re-derrubava a run inteira. `src/db.js:669-696@2af8070`, `src/commands.js:402-409@2af8070`.
