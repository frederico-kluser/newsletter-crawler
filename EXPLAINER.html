Como a atualização incremental não recaptura

Cada run re-visita as listagens inteiras — as listagens das 9 fontes são varridas de novo. O que impede a recaptura é o filtro only-new (only-new): três camadas descartam tudo que já é conhecido.

1 · known-url

Cada link descoberto é comparado com o known-url. Se a URL já existe no acervo, o item é descartado na hora — não é re-visitado nem re-enriquecido.

2 · INSERT OR IGNORE

No banco, a gravação usa INSERT OR IGNORE: mesmo que um link repetido chegue até a escrita, ele não duplica — a chave já existente o ignora.

3 · piso --since

O piso --since foi 2026-01-01: qualquer issue mais antiga que o piso nem entra na varredura.

O coração da atualização é o filtro only-new: é ele que faz “re-visitar tudo” valer a pena, porque o trabalho só acontece nos 57 itens que realmente não existiam — e os dois runs (#19 e #20) drenaram a fila até sobrarem só alvos inacessíveis. As issues novas de segunda foram capturadas e curadas (+54 curados), e a curadoria por IA fez o resto.

O requisito novo: reset apaga o snapshot do git

Antes, npm run reset -- --yes apagava só os dados do banco (wipeAll). O problema: o snapshot (webapp/public/data + webapp/public/api/v1) continuava commitado no git. E, enquanto o arquivo existisse, o guard fail-open do hook/deploy restauraria as notícias velhas.

O commit c44109c implementa isso no cmdReset: depois do wipeAll, executa git rm -r --ignore-unmatch -- webapp/public/data webapp/public/api/v1 (git rm). A detecção de repositório git é por .git (diretório ou arquivo) + rev-parse; sem repositório, cai para fs.rmSync; se o git rm falhar, avisa e segue (fail-open); e a recusa sem --yes continua intacta. A suíte fechou em 614/614, com 3 testes novos (repo git scratch, sem git, recusa) e revisão adversarial APPROVE (2 apontamentos não-bloqueantes).

Exemplo resolvido: siga uma issue nova do começo ao fim

Pegue uma edição de newsletter publicada depois de 2026-01-01 que ainda não está no acervo. O caminho:

  1. Listagem re-visitada: o run varre o arquivo da fonte e encontra a edição — junto com todas as antigas.
  2. Curadoria por IA: a issue é dividida por seção e um agente de IA separa os itens (notícia/ferramenta/release), guardando o blurb de cada link.
  3. Filtro only-new: cada link é comparado com o known-url. As URLs já capturadas são descartadas; as novas seguem.
  4. Gravação: a URL nova entra via INSERT OR IGNORE (sem duplicar), respeitando o piso --since 2026-01-01.
  5. Enriquecimento + qualificação: o crawler abre o link para extrair o corpo; se o alvo não responde, fica o blurb (fail-open). Depois vêm verificação, tags e resumo PT-BR em streaming.
  6. Snapshot + deploy: a exportação congela o acervo em JSON; o push na main publica — aqui, commit 99ddb45, no ar em 21s.

No fim, só o que era novo entrou: +57 artigos, de 13.701 para 13.758.

Por que o guard fail-open restauraria as notícias velhas (o raciocínio do requisito novo)

O hook de pre-push do projeto re-exporta o snapshot do SQLite local e auto-commita se houver dado novo — mas tem um guard fail-open: se o snapshot exportado for menor que o commitado (como aconteceria numa máquina com o banco recém-resetado, que exportaria vazio), ele restaura o snapshot antigo e segue sem commit.

Consequência antes do fix: você roda reset (banco vazio), mas o arquivo webapp/public/data continua no git. No próximo push, o hook exporta vazio → é menor que o commitado → restaura as notícias velhas. O reset “limpava” o banco, mas o site voltava ao passado no push seguinte.

O fix (c44109c) quebra essa armadilha na raiz: além do wipeAll, o reset git rm o snapshot. Sem arquivo no git, não há o que o guard restaurar — o estado vazio é vazio de verdade, também para o site.
